# 02_アーキテクチャー構成

## 1. 文書の目的
本書は、ソリューション構成、責務分離、実装制約、依存ルールを定義する。
ドメイン用語は 99_用語集 に従う。

## 2. ソリューション構成
基準は StudySession.slnx とする。

| 区分 | プロジェクト | 主責務 |
|---|---|---|
| src | StudySession.Domain | エンティティ、値オブジェクト、ドメインルール |
| src | StudySession.Application | ユースケース、アプリケーションサービス、入出力 DTO |
| src | StudySession.Infrastructure | DB 接続、Repository 実装、Dapper SQL 実行 |
| src | StudySession.Web | 画面/HTTP エンドポイント、認証、DI 構成 |
| src | StudySession.Batch | 手動実行コンソールバッチ、ユーザー登録処理 |
| tests | StudySession.DomainTests | Domain 単体テスト |
| tests | StudySession.ApplicationTests | Application 単体テスト |
| tests | StudySession.InfrastructureTests | Infrastructure 層テスト |
| tests | StudySession.WebTests | Web 層テスト |
| tests | StudySession.BatchTests | Batch 層テスト |
| tests | StudySession.IntegrationTests | 結合テスト（TestContainers） |

## 3. レイヤリング方針
1. Domain は外部ライブラリ依存を持たない。
2. Application は Domain のみ参照可能とする。
3. Infrastructure は Domain/Application の契約を実装する。
4. Web/Batch は Application に依存し、Infrastructure を DI で注入する。
5. 逆方向依存は禁止する。

## 4. データアクセス方針
1. ORM は使用しない。
2. Dapper と生 SQL を利用する。
3. SQL は Repository 層で管理し、プレースホルダによるパラメータ化を必須とする。
4. SQL インジェクション対策として文字列連結クエリを禁止する。

## 5. 接続情報管理
1. DB 接続情報は環境変数から取得する。
2. 推奨環境変数名: STUDY_DB_CONNECTION。
3. appsettings はローカル開発補助に限定し、本番秘密情報を保存しない。
4. Web と Batch は同一方針で接続情報を解決する。

## 6. 認証・認可方針
1. 認証方式は Cookie 認証とする。
2. users テーブルの login_id と password_hash で認証を行う。
3. password_hash は bcrypt で生成・検証する。
4. 認可はロールベースとし、User/Admin を扱う。
5. 勉強会作成は User/Admin の双方に許可する。

## 7. Web アプリケーション構成
1. 画面要件は 04_Webアプリ機能要件 を正本とする。
2. 主な画面はログイン、一覧、作成、詳細、403/404/500。
3. 画面遷移とバリデーションは Application のユースケースに委譲する。

## 8. バッチ構成
1. StudySession.Batch は手動実行コンソールとして運用する。
2. 実行モードは単件入力と CSV 一括取込の2種。
3. バッチ要件詳細は 05_ユーザー登録バッチ要件 を参照する。

## 9. 監視・ロギング
1. Web はアクセスログ、認証ログ、例外ログを出力する。
2. Batch は実行開始/終了、入力件数、成功件数、失敗件数、失敗理由を出力する。
3. ログフォーマットは時刻、レベル、機能、相関IDを含める。

## 10. テスト戦略
1. Domain/Application は単体テストを実装する。
2. Infrastructure は TestContainers を利用した PostgreSQL 結合テストを実装する。
3. Web は主要ユースケースの動作テストを実装する。
4. テスト方針の受入基準は 06_品質・非機能要件 に従う。

## 11. 将来拡張指針
1. 認証基盤連携を行う場合でも users テーブルとの整合を保持する。
2. API 分離を行う場合は Application 契約を変更せずプレゼンテーション層で吸収する。
3. バッチ定期実行化はスケジューラ層を追加して対応する。
