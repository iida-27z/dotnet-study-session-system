# 07_仕様レビュー観点チェックリスト

## 1. 目的
本書は、社内勉強会管理システムの仕様と実装が受入条件を満たしているかをレビューするためのチェックリストである。
レビューは「要件の適合性」「実装可能性」「運用準備性」の観点で行う。
用語は 99_用語集 に従う。

## 2. 記入ルール
- 各項目は Yes / No / N/A で判定する。
- No の場合は不具合や未対応事項を記録し、対応担当・期限を明記する。
- 実装完了を示す根拠として、画面・API・DB・テスト結果・ログを紐付ける。

## 3. 共通レビュー観点

### 3.1 システム全体
- [ ] 00_システム概要 の対象範囲と非スコープが明確である。
- [ ] 99_用語集 に定義されていない新用語が未使用である。
- [ ] Web アプリ、DB、ユーザー登録バッチの責務が重複していない。
- [ ] システムの主な価値が「勉強会企画」「出欠管理」「ユーザー登録」に整理されている。
- [ ] 本リリース対象と非対象が区別されている。

### 3.2 受入条件との整合
- [ ] 受入条件が業務要件と実装要件の両方に紐づいている。
- [ ] 画面上の表示要件と DB 要件が整合している。
- [ ] 例外系要件（403/404/500）が定義されている。
- [ ] 未確定事項が残っておらず、TBD が残っていない。

## 4. Web アプリ受入条件チェック

### 4.1 ログイン機能
- [ ] ログイン画面にユーザーIDとパスワードの入力欄がある。
- [ ] ログイン失敗時に再入力を促すメッセージが表示される。
- [ ] 認証成功時に一覧画面へ遷移する。
- [ ] 認証失敗時にパスワード平文がログや画面に出力されない。
- [ ] 未認証ユーザーが保護画面へアクセスした場合にログイン画面へ誘導される。

### 4.2 勉強会一覧
- [ ] 一覧画面に開催日時、テーマ、対面枠、リモート枠、出欠状況が表示される。
- [ ] 一覧画面の検索がキーワードまたは技術タグに対応している。
- [ ] 対面枠とリモート枠の対象外表示が最適化されている。
- [ ] 「満席」「未回答」「対面出席」「欠席」の表示が識別可能である。
- [ ] テーマ選択から詳細画面へ遷移できる。

### 4.3 勉強会作成
- [ ] 必須項目（テーマ、開始日時、終了日時、開催形式、定員）が定義どおりに検証される。
- [ ] 開始日時が終了日時より前であることを検証している。
- [ ] format ごとに対面枠/リモート枠の制約が守られている。
- [ ] 0 を許容する non-applicable の扱いが明確である。
- [ ] 登録後に一覧画面へ戻る動線がある。

### 4.4 勉強会詳細と出欠更新
- [ ] 詳細画面に概要、開催形式、開催日時、出欠締切が表示される。
- [ ] 対面のみ/リモートのみの開催形式に応じた選択制御がある。
- [ ] ユーザーの出欠更新がステータスとコメントで保存される。
- [ ] 開催前日 18:00 以降は更新を拒否または警告する。
- [ ] 定員超過時に更新が拒否される。
- [ ] 参加者名簿にユーザーID、氏名、ステータス、コメントが表示される。

### 4.5 エラー画面
- [ ] 403 画面に権限不足が明示されている。
- [ ] 404 画面に存在しないページを案内している。
- [ ] 500 画面に一時的障害を案内している。
- [ ] いずれも一覧画面に戻る導線がある。

## 5. 認証・認可受入条件チェック
- [ ] 認証方式が Cookie 認証として実装されている。
- [ ] パスワードはハッシュ保存されている。
- [ ] users テーブルの識別子とハッシュ項目が要件どおり制御されている。
- [ ] ロールが User / Admin の2種に整理されている。
- [ ] 管理者にのみバッチ運用の責務が割り当てられている。
- [ ] 全ユーザーが勉強会作成可能な設計になっている。
- [ ] 権限不足時に 403 画面へ誘導される。

## 6. DB・データモデル受入条件チェック
- [ ] DB は PostgreSQL を前提として設計されている。
- [ ] 接続文字列が環境変数から取得されるように構成されている。
- [ ] Dapper と生 SQL を用いて実装されている。
- [ ] 主要テーブルとして users / study_sessions / session_participations が定義されている。
- [ ] 主キー、外部キー、CHECK 制約が満たされている。
- [ ] users.password_hash は平文保存されていない。
- [ ] 監査項目 created_at / updated_at が主要テーブルに含まれる。
- [ ] 出欠ステータスの値域が要件どおりである。

## 7. バッチ受入条件チェック
- [ ] バッチは手動実行のコンソールアプリとして構成されている。
- [ ] 単件入力モードが実装されている。
- [ ] CSV 一括取込モードが実装されている。
- [ ] 必須項目である login_id / display_name / email / initial_password / role が検証される。
- [ ] 重複ユーザーの登録が拒否される。
- [ ] パスワードは登録時にハッシュ化される。
- [ ] 実行結果として成功件数と失敗件数が出力される。
- [ ] 失敗行の理由が監査ログ或いはログに残る。

## 8. 品質・非機能受入条件チェック
- [ ] 応答時間目標が満たされる。
- [ ] ログイン、一覧、詳細、出欠更新に対して性能基準が確認されている。
- [ ] 認証 Cookie に HttpOnly / Secure / SameSite が設定されている。
- [ ] CSRF 対策が適用されている。
- [ ] SQL インジェクション対策（パラメータ化）を採用している。
- [ ] XSS 対策（出力エスケープ）が適用されている。
- [ ] 監査ログが保存される。
- [ ] 例外通知とログ出力が運用可能なレベルにある。
- [ ] 403/404/500 の画面遷移が利用者に伝わる。

## 9. テスト評価観点
- [ ] Domain テストが実装されている。
- [ ] Application テストが実装されている。
- [ ] Web と Batch の主要ユースケースに対するテストが用意されている。
- [ ] TestContainers を用いた PostgreSQL 結合テストが実装されている。
- [ ] 異常系テスト（認証失敗、重複登録、定員超過、権限不足）が存在する。
- [ ] CI でテストが失敗した場合にマージを止める仕組みがある。
- [ ] カバレッジ目標が満たされている。

## 10. リリース判定チェック
- [ ] 必要な仕様書が揃っている。
- [ ] 環境変数一覧が定義されている。
- [ ] 実行手順書が存在する。
- [ ] バッチ運用手順が運用担当に説明可能である。
- [ ] 主要画面の受入確認が実施されている。
- [ ] 運用時に必要なログと監視対象を確認している。

## 11. 最終レビュー判定
- [ ] 受入条件をすべて満たしている。
- [ ] 残っている未解決事項が明示されている。
- [ ] 実装完了判定の最終承認者が記載されている。

## 12. 対応記録欄
| 項目 | 判定 | 不具合/未対応 | 対応担当 | 期限 |
|---|---|---|---|---|
| 例: ログイン失敗メッセージ | No | 画面表示の文言が要件と違う | 開発担当 | YYYY-MM-DD |
